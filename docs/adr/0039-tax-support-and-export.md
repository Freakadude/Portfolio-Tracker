# ADR 0039: Tax-support report, print to PDF, and an export that reads back

Status: accepted (2026-10-06). Covers FR-PF-11 and FR-TX-13.

## Context
FR-PF-11 asks for an annual report (values on 1 January and 31 December, deposits, withdrawals, income, costs, realized gains, change in unrealized) that exports to CSV and PDF, serving both the current fictitious-return system and the planned actual-return system. FR-TX-13 asks for an export of transactions and positions that re-imports cleanly through the CSV import.

## Decision
- The report is computed from what already exists, so it agrees with the rest of the app: values and holdings from the analytics context (one point per day, the last close on or before the date), realized results from the lot matches and income and costs from the yearly report of FR-TX-12, trade costs from the fees and taxes on buys and sells, and the unrealized result as value less cost basis of the valued holdings. Money put in and taken out follow the returns' definition of external flows (ADR 0014): daily changes in net contributions, so with cash tracking off purchases and deposits count as in, sales and withdrawals as out. The report says so.
- Both dates and both lists of holdings are shown, because the actual-return systems ask for the value on the reference date and the holdings behind it. A year not yet over runs to today and is marked partial; holdings with no price on a date are counted and called out instead of silently valued at zero.
- The PDF is the browser's: the page is print-styled (the sidebar and controls are hidden when printing) with a "Print or save as PDF" button. No PDF library was added (owner decision); the cost is that the file is made by the browser, not testable as a file here. The CSV is generated by the server.
- The transactions export has fixed columns (`FOLIO_HEADERS`): ISO dates, a dot as decimal separator, the exchange rate as the exact multiplier to euro, and the amount column holding the euro amount of cash and transfer-in rows (the ratio for a split). The import wizard recognises exactly that header row as a "folio" preset and fills the whole mapping, type map included. To make the round trip exact the importer learned a `taxes` column (trade taxes and withholding on income), which it had no place for; the rate is read as a multiplier, so nothing is converted twice. The export's `reference` column carries the original broker reference, or `folio-<id>`.
- Only posted transactions are exported; proposed ones are not part of the ledger. Names and notes starting with `=`, `+`, `-` or `@` get a leading apostrophe so a spreadsheet does not run them (as the realized report does), the one place a re-import is not byte-exact.
- Numbers in the CSV files are plain (no exponent, no trailing zeros).

## Consequences
The tax report states facts from the ledger; it applies no country's rules (the page says it is not tax advice). Fictitious-return and actual-return systems both start from the same four figures: values on the dates, flows, income and realized result.
